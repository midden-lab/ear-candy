# Runbook: Caddy / TLS configuration

HTTPS termination in production is handled by Caddy, running directly on
the Droplet host (not containerized) in front of the `ear-candy` container's
published port. Caddy auto-provisions and renews a Let's Encrypt certificate
for the configured domain with no manual TLS setup required.

## Source of truth

`infra/Caddyfile.template` is the versioned source of truth for the live
`/etc/caddy/Caddyfile` on the Droplet. `scripts/setup-droplet.sh` renders it
(substituting `__DOMAIN__` for the real domain) during initial provisioning
— see that script's "Configure Caddy" step.

Previously the Caddy config was generated by an inline heredoc in the setup
script and never checked in anywhere, which let the live config silently
drift from what the script would produce on a fresh run: the live Droplet
was hand-corrected to proxy to port 3000 (the app's real port) while the
script still generated `localhost:3001`, and nobody noticed until it was
checked directly (issue #58). Rendering from a single checked-in template
closes that gap — there's now something for a live edit to diff against.

## If you ever hand-edit `/etc/caddy/Caddyfile` on the Droplet

Back-port the change to `infra/Caddyfile.template` in this repo (swapping
the real domain back out for `__DOMAIN__`) in the same sitting. If you
don't, the next fresh Droplet provisioned from `setup-droplet.sh` will
silently regenerate the old, un-hand-edited config — exactly the failure
mode this file exists to prevent.

## Verifying the live config matches the template

```bash
ssh earcandy "cat /etc/caddy/Caddyfile"
```

Compare against `infra/Caddyfile.template` with the real domain substituted
in for `__DOMAIN__`. They should match exactly.

## Upgrading Caddy

Caddy comes from the Cloudsmith apt repo on the Droplet and is **not** upgraded
by CI or by the `deploy` job. Upgrade it by hand with the steps below (last
done 2.11.4 → 2.11.9 on 2026-11-21, plan 021).

**Never run `apt upgrade` / `apt full-upgrade` for this.** A blanket upgrade
would also pull containerd, Docker and kernel updates, which need a reboot
(the app container restarts) and deserve their own change. Upgrade only the one
package.

Before upgrading, read the release notes for every version between the
installed one and the target (GitHub releases for `caddyserver/caddy`) and look
for breaking changes affecting `reverse_proxy` or automatic HTTPS. For example,
2.11.6 added default 1-minute idle read/write timeouts and a 16 KiB request
header limit.

1. **Preflight** (on the Droplet, `ssh earcandy`):
   `df -h /` shows at least 3 GB free; `caddy version`; `systemctl is-active caddy`;
   `curl -sf http://localhost:3000/api/health`; note the status of
   `curl -sI https://<domain>/api/health` (expect 200).
2. **Save rollback material.** The Cloudsmith repo only lists the latest
   version, so `apt-get install caddy=<old>` will not work as a rollback:
   `cp -a /usr/bin/caddy /root/caddy-<old-version>.bin` and
   `cp -a /etc/caddy/Caddyfile /root/Caddyfile.pre-<new-version>`, then confirm
   `/root/caddy-<old-version>.bin version`.
3. **Upgrade only Caddy:**
   `DEBIAN_FRONTEND=noninteractive apt-get install -y --only-upgrade caddy -o Dpkg::Options::=--force-confold`
   (`--force-confold` keeps the live Caddyfile if apt asks about it).
4. **Validate:** `diff /etc/caddy/Caddyfile /root/Caddyfile.pre-<new-version>`
   is empty; `caddy validate --config /etc/caddy/Caddyfile` passes;
   `caddy version` shows the target version.
5. **Confirm the running process is the new binary.** The package normally
   restarts the service; compare `systemctl show caddy -p ActiveEnterTimestamp`
   with the time of the upgrade, and `systemctl restart caddy` if it is older.
6. **Verify:** `curl -sI https://<domain>/api/health` returns 200 with a valid
   certificate (no `-k`) and the body contains `"ok":true`; `docker ps` shows the
   `ear-candy` container with the same ID and uptime as before; and
   `journalctl -u caddy --since "10 min ago"` has no unexpected errors (a
   "Caddyfile input is not formatted" warning is harmless).

**Rollback** (if step 4, 5 or 6 fails):
`systemctl stop caddy && cp -a /root/caddy-<old-version>.bin /usr/bin/caddy && cp -a /root/Caddyfile.pre-<new-version> /etc/caddy/Caddyfile && systemctl start caddy`,
then repeat the step 6 checks. apt will keep offering the newer version; run
`apt-mark hold caddy` if you want to stay on the old one.

## Enabling HSTS (manual — and close to one-way)

**Live status (2026-11-23): staged rollout in progress.** The live Caddyfile now has
`header Strict-Transport-Security "max-age=86400"` (1 day), raised from 300 after
manual checks passed (`/root/Caddyfile.pre-hsts` is the original, `/root/Caddyfile.hsts-300`
the 5-minute version). **Remaining step: after a few days with no problems (not before
~2026-11-27), raise it to `max-age=31536000`** (the value already in the template) using
steps 3–5 below, then update this note. No `includeSubDomains`/`preload`; the apex
`positivesexed.com` is on Wix and must stay unaffected.

`infra/Caddyfile.template` now includes
`header Strict-Transport-Security "max-age=31536000"` (one year, **no**
`includeSubDomains`, **no** `preload`). That only affects a *fresh* Droplet
provisioned by `scripts/setup-droplet.sh`. **The live `/etc/caddy/Caddyfile` has
no HSTS header and nothing deploys one** — CI never touches Caddy. Applying it
to the running Droplet is a deliberate, manual decision (security audit L3).

**Read this first.** Once a browser has seen the header over HTTPS it refuses to
use plain HTTP for this hostname until `max-age` runs out — a year, per the
template. Removing the header later does **not** un-pin browsers that already
cached it. The only way to shorten it is to serve a smaller value (or
`max-age=0`) over working HTTPS and wait for each browser to revisit. That is
harmless while HTTPS keeps working and painful if it ever breaks (an expired or
misconfigured certificate becomes a hard failure with no click-through). Do not
add `includeSubDomains` or `preload` unless you are certain every subdomain will
be HTTPS-only indefinitely.

**Recommended: stage it** — start with a short lifetime so a mistake expires in
minutes, then raise it:

1. Back up the live config on the Droplet:
   `cp -a /etc/caddy/Caddyfile /root/Caddyfile.pre-hsts`.
2. Edit `/etc/caddy/Caddyfile` and add this line inside the site block, above
   `reverse_proxy`: `header Strict-Transport-Security "max-age=300"` (5 minutes).
3. Validate before touching the running service:
   `caddy validate --config /etc/caddy/Caddyfile`.
4. Apply it: `systemctl reload caddy`.
5. Verify:
   `curl -sI https://<domain> | grep -i strict-transport-security` shows
   `strict-transport-security: max-age=300`, and
   `curl -sf https://<domain>/api/health` still returns `"ok":true`.
6. Use the site for a while (browse, play an episode, log in to admin). When
   you are confident, change `max-age=300` to `max-age=31536000` (the value in
   the template), repeat steps 3–5.

**To undo** (the header only; already-pinned browsers keep their lifetime):
restore the backup with `cp -a /root/Caddyfile.pre-hsts /etc/caddy/Caddyfile`
and `systemctl reload caddy`. To actively shorten browsers' pin instead, serve
`max-age=0` for as long as your visitors take to come back.

Keep the live config and the template in step (see above): if you apply HSTS by
hand with a different value, back-port it to `infra/Caddyfile.template`.

High Severity

H1 — No absolute session expiry

Auth
Location
server/src/routes/admin/auth.ts (reply.setCookie, login handler)
Scenario
The admin_session cookie is set with no maxAge/expires. It's a browser-session cookie in theory, but the signed value carries no timestamp, so requireAdmin accepts it indefinitely as long as the signature validates. A cookie exfiltrated via XSS, a shared/compromised machine, or a browser that restores sessions across restarts remains valid with no time bound and no server-side way to force-expire it.
Remediation
Set a maxAge (e.g. 12–24h) on the cookie, and/or embed an issued-at timestamp in the signed value that requireAdmin checks against a max session age.

H2 — GitHub Actions script injection via unescaped interpolation

Infra
Location
.github/workflows/ci-cd.yml — deploy job script block and the e2e job's "Start test container" step
Scenario
Secrets and context values (secrets.GHCR_PAT, secrets.COOKIE_SECRET, secrets.ADMIN_PASSWORD_HASH, github.sha, github.actor) are spliced directly into script:/run: text via ${{ }}, rather than passed through env: and referenced as $VAR. This is GitHub's documented script-injection anti-pattern: if any interpolated value ever contains shell metacharacters, it becomes literal shell syntax with full execution rights on the job holding SSH_PRIVATE_KEY to the production Droplet. Current secret formats don't contain breaking characters today, but nothing prevents a future value from doing so, and the pattern is fragile by construction.
Remediation
Pass every interpolated value via a step-level env: block and reference it as "$VAR_NAME" inside the script — never splice ${{ }} directly into script text.

H3 — Third-party Actions & base images pinned to mutable tags

Infra
Location
Every uses: line in .github/workflows/ci-cd.yml (notably appleboy/ssh-action@v1.0.3, which executes the entire deploy script); node:20-alpine throughout the Dockerfile
Scenario
Tags are mutable. If any pinned action's upstream repo were compromised and its tag re-pointed, the next CI run silently executes attacker code with access to every secret in the workflow — GHCR_PAT, SSH_PRIVATE_KEY, DROPLET_IP, COOKIE_SECRET, ADMIN_PASSWORD_HASH. That's full production root access plus registry write in one compromise, concentrated in appleboy/ssh-action specifically. Rated High (not Medium) because of the unusually high secret concentration this pipeline carries relative to a typical CI job.
Remediation
Pin appleboy/ssh-action — ideally all actions — to a full commit SHA with a comment noting the version. Use Dependabot/Renovate to keep SHA pins current. Pin node:20-alpine to a digest for reproducible builds.

H4 — Shared login-lockout bucket behind the production reverse proxy

Auth + Infra (cross-referenced)
Location
server/src/routes/admin/auth.ts (lockout logic, keyed on req.ip); server/src/app.ts (no trustProxy configured); production Caddy reverse proxy per planning/2026-07-10-do-droplet-setup.md
Scenario
Fastify defaults to trustProxy: false, so req.ip reflects the direct TCP peer — which, in production, is Caddy, not the real client. Every request arrives from Caddy's address, collapsing every real visitor into one shared lockout bucket. Ten failed login attempts from anywhere on the internet locks out the legitimate admin too — a trivial, unauthenticated denial-of-service against the only account that can manage the site. This was flagged by the Auth reviewer as a future/hypothetical risk ("if a reverse proxy is ever introduced") but the Infra reviewer independently confirmed Caddy is already deployed in production today, making this a live issue, not a forward-looking one.
Remediation
Configure Fastify's trustProxy to trust only Caddy's specific address (loopback/internal network), then verify req.ip correctly reflects the real client IP from X-Forwarded-For in production. Do not blanket-trust all proxy headers.

Medium Severity

M1 — No way to revoke a specific session

Auth
Location
server/src/routes/admin/auth.ts (/admin/logout)
Scenario
logout only clears the current browser's cookie. There's no server-side session store, so a stolen/duplicated cookie held elsewhere remains valid — logging out locally does nothing to revoke a copy an attacker holds. Rotating COOKIE_SECRET invalidates everything, but that's a blunt, whole-secret rotation requiring a redeploy, not a targeted "sign out everywhere."
Remediation
Track a session version/generation number (e.g. a new settings column) embedded in and checked against the signed cookie, bumpable on demand for a real mass-invalidate without a redeploy.

M2 — Deploy's image-digest "verification" doesn't verify anything

Infra
Location
.github/workflows/ci-cd.yml, deploy job, "Verifying image digest..." step
Scenario
docker inspect "$IMAGE" --format='{{.RepoDigests}}' > /dev/null discards its own output and compares against nothing. It proves the image has some digest, not that it's the correct, untampered one — a misleading log line implying a real integrity gate exists when it doesn't. A compromised registry or credential would deploy a malicious image with zero real gate.
Remediation
Either remove the misleading step or make it real: pass the digest produced by the build job through as a job output and assert equality in deploy before running the image.

M3 — Production container runs as root

Infra
Location
Dockerfile, final runner stage — no USER directive
Scenario
The Fastify process runs as root inside the container. A remote-code-execution bug in the app or a dependency would grant root inside the container immediately, skipping the privilege-escalation step an attacker would otherwise need.
Remediation
Add a non-root user in the runner stage and switch to it with USER; verify data/uploads ownership/permissions still allow writes.

M4 — Backups exist but aren't offsite

Infra
Location
backup.sh cron job (daily, 3 AM, 14-day retention) per planning/2026-07-10-deploy-do-gitlab.md
Scenario
Backups genuinely exist (confirmed, not assumed away) but live on the same Droplet as the primary data. Total disk failure, a compromised root SSH key, or Droplet/account loss destroys both primary data and backups simultaneously — this is same-host snapshotting, not real disaster recovery.
Remediation
Ship backups offsite on a schedule (S3/Spaces/Backblaze, or a second Droplet/region) — even adding a simple rclone/s3 cp to the existing cron script closes this gap.

M5 — Audio/favicon uploads skip content-based validation

AppSec
Location
server/src/routes/admin/upload.ts, upload-favicon.ts
Scenario
Both routes accept a file based solely on client-supplied filename extension and multipart Content-Type — both fully attacker-controlled via a raw crafted request. Unlike upload-image.ts, which runs sharp(buffer).metadata() as a magic-byte check, audio/favicon uploads never verify the bytes match the claimed type. Mitigated by X-Content-Type-Options: nosniff and extension-derived static serving (not an XSS path), but a real inconsistency letting junk content persist under a trusted-looking path.
Remediation
Apply the same magic-byte validation already used for cover art (or a lightweight check via a library like file-type) to audio and favicon uploads.

Low Severity

L1 — isValidMediaPath checks prefix only

AppSec
Location
server/src/utils/validation.ts
Scenario
Validates favicon_path/cover_art_path via startsWith('/images/') or startsWith('/audio/') only — no check for .. traversal or matching the expected UUID-filename shape. Likely not exploitable end-to-end since @fastify/static independently blocks traversal, but provides no real app-level defense-in-depth.
Remediation
Also reject .. segments and/or match the generated-filename pattern exactly.

L2 — No minimum entropy/length check on COOKIE_SECRET

Auth
Location
server/src/app.ts (startup validation)
Scenario
Only checked for presence, not strength. An operator manually editing .env could set a trivially short/guessable secret, letting an attacker forge valid session cookies offline via HMAC brute-force.
Remediation
Reject startup if COOKIE_SECRET.length is below a reasonable floor (e.g. 32 chars); make setup's generated secrets already satisfy this.

L3 — No in-app password rotation

Auth
Location
server/src/routes/admin/auth.ts (ADMIN_PASSWORD_HASH env var)
Scenario
Rotation requires regenerating a bcrypt hash and updating a GitHub secret, then redeploying — slow enough that rotation likely happens rarely, widening the exposure window after any suspected compromise. Already tracked separately as a known product gap; bundled here with M1 since neither has a way to force a mass-logout on rotation either.
Remediation
Already scoped as a follow-up feature; pair it with a session-invalidation mechanism (see M1) when implemented.

L4 — No workflow-level default permissions:

Infra
Location
.github/workflows/ci-cd.yml (top level)
Scenario
Only build explicitly scopes its token. lint/test/typecheck/e2e/deploy inherit the repo's default GITHUB_TOKEN permissions, likely broader than needed since none of them call the GitHub API. Defense-in-depth gap, not an active exploit path.
Remediation
Add a top-level permissions: contents: read default, overriding per-job only where write access is genuinely required.

L5 — No automated dependency vulnerability scanning

Infra
Location
Repo-wide — no Dependabot config
Scenario
npm audit isn't run in CI and nothing opens PRs for vulnerable transitive dependencies across a nontrivial dependency tree (sharp, bcrypt, better-sqlite3, Fastify plugins). Vulnerabilities can sit unnoticed indefinitely.
Remediation
Add Dependabot/Renovate config for both server/ and client/ npm ecosystems; optionally add an npm audit --audit-level=high step to CI.

L6 — Caddy/TLS config lives outside version control

Infra
Location
Provisioned manually per planning/2026-07-10-do-droplet-setup.md — no Caddyfile tracked in-repo
Scenario
HTTPS termination is real (confirmed, not assumed) via Caddy + Let's Encrypt, but the config isn't versioned. Recreating it after a Droplet loss depends entirely on a human correctly following a markdown runbook, with no drift detection if hand-edited later.
Remediation
Commit the Caddyfile to this repo even if applied manually, and note the manual-apply step explicitly in the DR runbook.

Confirmed Solid (Not Findings)

Explicitly verified by the panel and found sound — listed so this reads as a real audit trail, not a one-sided list of problems.

  • Stored-XSS SVG favicon fix — verified still in place and correct in upload-favicon.ts.
  • SQL injection — all three PATCH handlers (episodes, seasons, settings) enforce an allowlist before building dynamic SET clauses; no way found to smuggle an unlisted field into raw SQL.
  • CSRF — admin_session cookie uses sameSite: 'strict' + httpOnly, the strongest practical cookie-based mitigation; no separate CSRF token needed.
  • XSS via admin text fields — zero dangerouslySetInnerHTML/innerHTML usage anywhere client-side; React's default escaping applies universally. accent_color is applied via CSSStyleDeclaration.setProperty, not string-concatenated into a stylesheet — no CSS-injection breakout even with adversarial input.
  • Content-Security-Policy — strict and well-reasoned: script-src 'self' (no unsafe-inline/eval), object-src 'none', frame-ancestors 'none'.
  • pull_request (not pull_request_target) used for the PR trigger, and the repo is private — the classic "malicious fork PR steals secrets" vulnerability class doesn't apply here.
  • Backups exist — daily cron with 14-day retention (corrects an assumption the Infra reviewer would otherwise have made from the repo alone; see M4 for the offsite gap that remains).
  • TLS exists in production — Caddy + Let's Encrypt (corrects an assumption the reviewer would otherwise have made; see L6 for the config-versioning gap that remains).
  • AdminLayout's session-check-on-mount is genuine defense-in-depth, not a false sense of security — the server still enforces requireAdmin on every real admin API call regardless.
  • Dependency versions (Fastify 5.10, sharp 0.35, better-sqlite3 12.x, React 19) all current in a manual skim (a full npm audit run is recommended per L5, not performed as part of this pass).
